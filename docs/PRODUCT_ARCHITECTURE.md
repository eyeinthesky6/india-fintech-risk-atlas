# Product architecture — India Fintech Risk Atlas
Status: living product architecture guide; supersedes earlier drafts and persona-centric site models.

## Core Design Philosophy: Simple & Unbloated
1. **Ready-Reckoner Topic Structure Over Persona Silos:**
   We abandoned persona-based content presentation as a primary navigation structure. If applied across all of Indian fintech, persona roles would expand into dozens of overlapping profiles and become completely unmanageable.
   Instead, content is organized directly by **Ready-Reckoner risk patterns and topics** (`UPI-001` through `UPI-016`). 
2. **Personas as Scoped Filters Only:**
   Participant roles are rail-specific and used **strictly as an optional secondary table filter at maximum** (e.g. within the `## What to do` checklist).
   For UPI, these are strictly limited to the 6 core ecosystem participants:
   - `tpap` (Third-Party Application Providers: PhonePe, Google Pay, CRED)
   - `psp-bank` (PSP Banks)
   - `remitter-bank` (Issuer Banks)
   - `beneficiary-bank` (Acquirer / Beneficiary Banks)
   - `aggregator` (Payment Aggregators: Razorpay, Cashfree, Juspay)
   - `customer` (Payer / End User)
3. **Pragmatic v1 Scope (UPI Rail First):**
   Future cross-product abstractions (such as global `PAT-*` and `CTRL-*` mappings across Cards, NetBanking, and Lending) are explicitly parked in the **v2+ post-launch roadmap**. In v1, the product is focused solely on UPI (`UPI-001` to `UPI-016`) without unnecessary indirection or premature complexity.

## Audience and primary tasks
Product manager: find fraud patterns and recommended checks for a product.
Risk analyst: compare indicators, data requirements, false positives and response options.
Founder/investor: understand mechanisms, operational risks and product-specific differences.
Researcher: trace each claim to an original dated source and follow related records.
Contributor: submit a well-sourced correction through GitHub PR.

## Canonical Content Architecture
- **Canonical Topic Records:** Stored as portable Markdown under `src/content/docs/upi/<ID>.md`.
- **Double-Ledger Audit:** Each record is paired 1:1 with claim assertions in `research/evidence/<ID>.md` and 12-item declarations in `research/attestations/<ID>.md`.
- **Five Evidence Layers:**
  1. `Regulatory` (`official`)
  2. `Industry practice` (`industry`)
  3. `Community insight` (`practitioner`)
  4. `Research & academic` (`research`)
  5. `Atlas guidance` (`atlas`)

## Navigation & Discovery
Home > UPI Catalog > Topic Record (Ready-Reckoner 6-part layout)
- Search: Pagefind full-text static search over Markdown.
- Filtering: Optional client-side role filtering across the Ready-Reckoner `What to do` table.
Short summary; product/actor applicability; explanation; possible signals; suggested checks; limitations/false positives; customer impact; related records.
Inline citation numbers at the claim. Bottom 'References' section contains publisher, exact title, dated version, section and link. 'Source applicability' is visible for normative claims. 'Suggest edit' links to GitHub.
No generic disclaimer as a substitute for correct source scoping.

## Content repository structure
- `src/content/docs/upi/<ID>.md` are canonical, human-authored Markdown topic records.
- `src/content/docs/` provides foundational guides (`methodology.md`, `evidence-policy.md`, `contribute.md`, `licensing.md`).
- `research/evidence/<ID>.md` maintains claim-by-claim assertion ledgers.
- `research/attestations/<ID>.md` stores 12-item pre-commit verification declarations.
- `dist/` is the compiled static website generated by `npm run build` for GitHub Pages. Zero runtime database or backend required.

## Volume / evolution
Start 1 product with 15–25 fully checked records and 30–80 sources as a target, not a verified inventory. Expand product by product. A pattern reused by 5 products stays one record. Static architecture targets thousands of records without needing a database. Introduce richer faceted search only after testing actual reader demand.

## Quality and governance
Draft -> source-checked -> independently-reviewed -> published -> needs-reverification -> archived.
No agent can promote its own record to independently-reviewed. Content validation checks structure, IDs, links and metadata; human/editorial verification checks truth and applicability. Source withdrawal triggers affected-claim review.
